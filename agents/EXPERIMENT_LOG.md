# Experiment log: forked environments for GRPO rollouts (OSWorld + WebArena), 2026-10-25 to 10-30

This is the full record of the experiments for the MLSys paper: what was run, on which machine, with what result, and
where every output, checkpoint and script lives. The paper compares tfork with CRIU and AgentENV (AENV) and studies
environment-side policies (speculation, screen/prefix cache, fork ordering) for the long tail of GRPO rollouts. The
model itself was never changed by these policies; only the environment was.

- OSWorld harness: `agents/osworld_rl/` (README.md = how it works, SETUP.md = host setup).
- WebArena harness: `agents/webarena_rl/` (the teammate's runner plus our patches, see section 6).
- Every run as a table: `agents/osworld_rl/data/RUNS.md` (154 runs on 06) and `agents/webarena_rl/runs/RUNS.md`
  (runs on 08). Both are generated by `python3 agents/osworld_rl/run_index.py <dir>`; times are PDT.

## 2. Timeline

### 10-25: environments
- OSWorld desktop = KDE webtop + OSWorld server (`ghcr.io/wuklab/webtop:ubuntu-kde-osworld`; patch in
  `osworld_rl/setup/ubuntu-img-kde-osworld.patch`). GNOME was dropped: tfork forks of it fail 30-50% of the time
  (dconf ghost files).
- All three systems verified on one shared desktop start script (`desk_osw.sh`): 8-copy fork tfork ~4.6 s,
  stock CRIU ~28 s, AENV ~1.4 s.

### 10-26: CRIU baseline + first memory comparisons
- CRIU baseline = our CRIU in CKPT mode (N serial `clone --live --copies=1 --tfork-full-memcopy`).
- `osw_loop.py --exp osw_criu --system criu --epochs 4` (GRPO, adapters `pod_backup/osw_criu/`).
- One-epoch memory comparisons `osw_{criu,tfork,aenv}32_once`, `_capped`, `osw_*29`. Fixes found on the way:
  `--fork-concurrency` (4 groups fork at once), empty `/etc/hosts` and dead socat relay in copies, `setpriv` instead of
  `runuser` (ETOOMANYREFS), LibreOffice `--norestore` wrappers, fixed `containers-os4agent.conf` (parallel clones raced).
- Thunderbird, VS Code and OS tasks excluded (netlink sockets, ~775-thread restores).

### 10-27: replay comparison, tfork retry root cause
- Recording `rec32v2_tfork` (live, base model, 32 tasks x 8), replayed on each system: `replay32_{tfork,criu,aenv}`.
- AENV: its proxy cuts requests at 30 s; the runner now relays straight into the VM (`Forwarder`).
- tfork retries were caused by per-copy btrfs snapshots (8 copies re-reading binaries from SATA, past tfork's hard-coded
  10 s restore wait). `--overlay-rootfs 1` (now default) fixed it: `replay32_tfork_overlay`, 0 retries.
- Result (32 groups x 8, `--parallel 8`): PSS per group after fork tfork 1.31 / CRIU 5.42 / AENV 2.57 GiB; after
  rollouts 2.95 / 7.06 / 6.58; peak PSS 32.8 / 64.5 / 66.0 GiB; run time 29 / 37 / 47 min.
- Base fork (2-level tree, `--base-fork 1`) needed the `podman-tfork.sh` cgroup-path fix
  (`osworld_rl/setup/podman-tfork-cgroup-path.patch`; uncommitted on 06, backup `/mnt/ssd2/vikranth/podman-tfork.sh.bak`).
- Code cleanup: everything not needed moved to `attic/`.

### 10-29: GRPO reward curves, speculative execution
- `grpo_tfork16`: 10 epochs, 16 tasks x 8, tfork. Successes per epoch 11, 10, 13, 15, 14, 15, 13, 11, 15, 11 of 128:
  flat, because only 1-2 groups per epoch had reward variance. `data/checkpoints/grpo_tfork16/` (loop.jsonl,

- Speculative execution (`--spec-exec 2 --spec-max-forks 10`, TAGE top-2 forks per step): 8x8 tail replay
  16.3 -> 13.7 min (-16%); without the fork cap no gain (~54 clones at once). Bugs fixed: a failed clone-of-clone
  deleted the group's shared snapshot; Chromium can SIGSEGV under CRIU's parasite and leave CRIU's nft lock behind.

### 10-30 (afternoon): later GRPO epochs and why reward fell
- Solved per epoch (of 128): 51 / 45 / 47 / 49 / 42 (`rec128_shot`, `rec128e2..e5_shot`); epoch 5 rerun at think
  budget 1,536 (`rec128e5b_shot`) solved 46, invalid actions 86 -> 51, 27.2 min.
- Cause: thinking grows every epoch (median 597 -> 1,109 tokens; over budget 30% -> 56%; invalid actions 19 -> 86),
  and the PPO-clipped fraction grows per update (1.4% -> 4.8% -> 10% -> 9.4%). The 6 never-solved tasks give no signal.
- `train_grpo.py` now runs data parallel under torchrun (equivalence checked); pol6s was trained on the 2xH100 pod.

Analysis (`runs/wa_*.py`): per step model 1.1 s vs env 2.0 s; last group (task 65) = setup 54 s + fork queue and fork
256 s + rollouts 75 s. Ceilings: every step a cache hit -4.6%, no env time -10.5%, no fork queue -47.6%.
TAGE top-1 61-62%; free-fork speculation bound -9.1%, realistic ~0% (forks 47-67 s >> model time).
Longest-first fork ordering (simulated, `wa_order.py`): -9.5% now; with rollouts x2 -20%, x3 -25%, x5 -16%.
With thinking-model latency (x15): longest-first -12.3%, prefix cache -2.0%, both -14.3%.

Why WebArena forks are slow: each copy is Chromium + MySQL + Magento PHP (cgroup ~587 MiB, 430 MiB of it file pages;
OSWorld desktop ~775 MiB RSS but 5 s for 8 copies). One 8-copy clone takes 32-41 s alone; concurrent clones
contend for CPU/disk (57 s at 4, 108 s at 8, failures at 16), so throughput saturates at ~1 clone per 14 s.

WebArena GRPO training attempt: all 16 groups had zero reward variance (only tasks 94, 95, 103, 121 of 32 are mixed),
so nothing was trained. Script `osworld_rl/pod/train_wa_e1.sh`, data `osworld_rl/pod/data/wa_e1/`.
